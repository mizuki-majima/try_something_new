## 再レビュー（2回目、2026-10-07）

### Context

D1〜D13 の修正（コミット fef7802）を別のエージェントが再レビューし、実際に動かして次を確かめた。

- **Critical（NF-1）**: 費用に上限が無い。`PATCH /api/me` は回数の上限なしに、ニックネームや進捗公開を変えるたびに本人のチャレンジを全部書き直す。文字の上限が UTF-16 の長さなので、結合文字を詰めた「1文字」で約 1.5KB 保存できる。読み込みですぐに大きな項目を200件持てる。テーブルにスループットの上限が無い。匿名アカウント4つで1時間 約 $10、最大 約 $100 になりうる（目標は月 $1）
- Medium: 消して読み込み直すと、止めたカードを公開し直せ、1日組から外したものも戻る（NF-2）。IPv6 の /64 では1軒（日本の IPoE は /56）で上限の256倍のアカウントを作れる（security-3）。1人が24時間寝かせた3アカウントで何でも隠せる（security-4）。作成の 429 をすべて「1日の上限」として捨てるので、API Gateway の一時的なスロットルで新しいチャレンジが消える（r2-web-1）
- Low: 読み込んだチャレンジの振り返り直しで判定の内訳がマイナスになる（NF-3）、IP の鍵が無いと公開の既定の鍵で動き続ける（NF-4）、同時の読み込みで上限を超える（NF-5）、origin-verify の手順 3 がデプロイの成否を見ていない・空の `ORIGIN_VERIFY` で確認が外れる（NF-6）、規約・通報画面・運用の文書が実際と違う（r2-web-2/3/6、r2-docs-1）

### Decision

| | 決定 | 選ばなかった案 |
|---|---|---|
| R1 | (a) `PATCH /api/me` でニックネーム・進捗公開を変えるのは1人1日10回（日本時間の日付。進捗公開をオフにするのは R13 で数えない） (b) 公開用の情報の書き直しは、中身が変わる項目だけ（読み込んだまま・非表示・公開しない終わったものは触らない） (c) 保存する文字は書記素の数に加え、UTF-8 で `max × 4 + 32` バイトまで (d) DynamoDB のテーブルと各 GSI にオンデマンドの最大スループット（読み込み 400・書き込み 100 ユニット/秒。読み込みは R15 で 1000）を費用の上限として付け、スロットルのアラーム（`alertEmail` 指定時） | プロビジョンドに切り替える（普段の費用と運用が増える）、上限なしで予算のメールだけに頼る（タグを有効にするまで $0 のまま。気づくまでに費用が出る） |
| R2 | モデレーションをチャレンジの項目の外に残す: カードや1日組を非表示・削除するときに `MOD#<chId>` / `META`（gsi2 `AUTHOR#<持ち主>` でアカウント削除と一緒に消える。R12 でアカウント削除後も残すように変更。shareModerated・memberHidden）を書き、`POST /api/shares` と読み込みが見る。管理画面の復元で該当の印を外す | 止めた内容と同じ文面を探して止める（判定が難しく、誤検知する） |

| R4 | Lambda（`IP_HASH_KEY_PARAM` あり）では鍵が無い・読めないと起動しない（500 と `ApiErrors`）。既定の鍵はテストとローカルだけ | 起動ごとの乱数の鍵で動き続ける（気づけず、レート制限の数がコールドスタートごとに数え直しになる） |

### Consequences

- DynamoDB の上限は**1時間あたりの速さ**を抑えるだけで、月の合計の上限ではない（R16 で訂正。前は「1時間 約 $1.9 で止まる」と書いていた）。いまの上限（R15 のあと）では、テーブルか GSI 1つにつき読み込み 約 $0.51/時・書き込み 約 $0.26/時、全部が上限まで使われると 約 $3.1/時。上限の少し下で使われ続けるとスロットルは起きず `DynamoThrottles` も鳴らないので、続く使い方に気づけるのは予算のメールだけ。上限に当たっている間は、ほかの人の読み込み（認証の読み込みを含む）も書き込みも遅れる（API の SDK がやり直し、通らなければ 500。書き込みは端末の送信待ちに残り、あとで送られる）。上限に当たると `DynamoThrottles` のメールで分かる
- 既存のテーブルへの上限の追加は、CloudFormation の更新で置き換えにならない（データはそのまま）
- DynamoDB 以外（CloudFront・API Gateway・Lambda・Logs）は、ステージの上限 20 rps で月 $170 前後までありうる。2xx か 429 で終わるので `Api5xx` は鳴らず、気づけるのは予算のメールだけ（費用配分タグの有効化が前提）。API Gateway のリクエスト数のアラームは今回は足さない（下の「見直す条件」）
- origin-verify の入れ替えの手順 3 には AWS CLI と、`cloudformation:DescribeStacks`・`cloudfront:GetDistribution` の権限が要る（デプロイできる認証情報なら持っている）
- IP のハッシュ鍵が無いままデプロイすると、API は止まる（500）。`npm run deploy` は `--check` で先に止めるが、`cd infra && npx cdk deploy` で直接デプロイするときは先に `--check` を実行する
- **CEO 承認済み**: D12（お問い合わせの返信先）は [#3](https://github.com/mizuki-majima/try_something_new/issues/3) で案A（2026-10-07、[ADR 0005](0005-pilot-approval.md)）。PRODUCT.md の Do Not Build の例外として確定
- 見直す条件: 上限（スループット・プロフィール変更・アカウント作成の全体の上限）に、荒らしではない利用で当たったら上限を見直す。予算のタグを有効にできない、または DynamoDB 以外の費用の荒らしが起きたら、API Gateway のリクエスト数のアラームを足す

## 最終確認（3回目、2026-10-07）

### Context

R1〜R10 の修正（コミット 9736914）を別のエージェント2つが確認した。Gate 5 は通過（Critical / High なし）。残った Medium / Low を、実際に動かして確かめたうえで次のように直す。

- Medium（R3-API-1・N3-3）: アカウント作成の全体の上限（1時間300件）を、1つの IPv6 /48（無料のトンネルで手に入る。/56 が256個）や IPv4 15個で使い切れる。使い切られるとその1時間、新しく来た人は全員 429 で、運営者には何も届かない
- Medium（R3-API-2・N3-1・N3-2）: 読み込みの上限（400 RRU/秒）は認証の読み込みにも効くので、読み込みで大きくしたアカウント1つが毎秒1〜2回 `GET /api/challenges` を呼ぶだけで全員の API が 500 になる。管理画面の PILOT の集計はテーブル全体をスキャンして上限を使い切り、大きなテーブルでは30秒でタイムアウトする
- Medium（R3-API-3）: `MOD#<chId>` が持ち主の gsi2 に付いているので、アカウントを消すと一緒に消え、新しいアカウントで読み込み直すと止めたカードを公開し直せる
- Low: 進捗公開をオフにするのも1日10回の上限に数えるので、使い切ると1日組から外れられない（R3-API-4）。読み込みで1つのひとことが新しいバイト数の上限を超えると、チャレンジごと読み込まれない（R3-API-5）。文書: `status:needs-ceo` の Issue（#3）があるのに「まだ無い」（N3-4）、式のアラームの費用（N3-5）、DynamoDB の費用を「止まる」と書いている（N3-6）

### Decision

| | 決定 | 選ばなかった案 |
|---|---|---|
| R11 | アカウント作成は、IP ごと（IPv4 アドレス・IPv6 /56）1時間20件のまま、ネットワークごと（IPv4 /16・IPv6 /48、秘密鍵つきのハッシュ）1時間60件を足し、全体の上限は費用の天井として1時間2000件に上げる。全体の上限に当たったときの警告ログ（`global session ceiling reached`）を CloudWatch Logs のメトリクスフィルタで数え、アラーム `SessionCeiling`（`alertEmail` 指定時。5分間に1回以上） | 全体の上限をなくす（多くのネットワークを持つ相手への費用の天井が無くなる）、/24 で数える（IPv4 の1つの範囲を持つ相手には足りない） |
| R12 | `MOD#<chId>` は持ち主の gsi2（`AUTHOR#`）を持たない（中身はチャレンジの ID と印だけで、個人に結びつく情報は無い）。アカウントを消しても残るので、新しいアカウントが同じ ID を読み込んでも止めたまま。前の版で書いた印は、アカウント削除のときに gsi2 だけを外して残す | アカウント削除で CHREF を残し、新しいアカウントには別の ID を振る（ID の項目が人に結びついたまま残る） |

| R14 | 読み込みで、ひとことが今の決まり（UTF-8 の上限など）に合わないときは、そのひとことだけを読み込まず、印とチャレンジは残す（`notesDropped` で件数を返し、画面に出す）。保存する大きさが上限を超えた入力のエラーは「あと N 文字減らしてください」と言う | 切り詰めて残す（文の途中で切れる）、チャレンジごと読み込まない（30日の記録が丸ごと消える） |

### Consequences

- 1つのネットワーク（IPv4 /16・IPv6 /48）からは1時間60件までしかアカウントを作れない。携帯の CGNAT など大きな範囲を多くの人が共有する場合、口コミで一気に人が来ると断られる人が出うる（帯で「混み合っています」と出て、端末の中では使える）。全体の上限（2000件）を使い切るには、34以上のネットワークが要る
- `SessionCeiling` のアラームが加わり、アラームのメトリクスは12個（`Api5xx`・`ApiErrors`・`ReminderErrors`・`SessionCeiling` が1つずつ、`DynamoThrottles` が8つ）。アカウントの無料枠（10個）が他のプロジェクトで使われていれば、アラームだけで月 約 $1.2 になり、SPEC の目標（月 $1 未満）を超える。下げるなら `DynamoThrottles` をテーブルの `ReadThrottleEvents`・`WriteThrottleEvents` の2つにする（月 約 $0.6）。メトリクスフィルタのカスタムメトリクスは警告が出た時間だけ課金（普段は $0）
- 読み込みの上限を上げたので、上限まで使われたときの費用は上がる（テーブルと GSI 3つ全部で 約 $3.1/時。前は 約 $1.9/時）。それでも1つのクライアントは、読み込みで大きくしたアカウント（約 3MB、1回 約 390 RRU）で毎秒3回ほど `GET /api/challenges` を呼べばテーブルの上限に届く（ステージの上限 20 rps より下）。そのときは `DynamoThrottles` が鳴る。止める道具（アカウントを止める・ページ分け・INCLUDE の射影）は、PILOT で必要になったら足す
- PILOT の集計は20秒で打ち切るので、テーブルがとても大きくなると数字が少なめに出る（管理画面に出る）。打ち切るまでの間は、集計がテーブルの読み込みの上限の大部分を使いうる（管理トークンを持つ人だけが起こせる）
- `MOD#<chId>` はアカウントを消しても残る（チャレンジの ID と印だけ）。プライバシーポリシーは「すべて消える」とは書いておらず、消える項目を並べているので変えない。R11 で IP から作るハッシュ値の種類が増えたので、その行だけを直した
- 読み込みの結果の表示に、読み込まなかったひとことの件数が加わる（「長すぎるひとこと N件は読み込みませんでした」）
- 見直す条件: ネットワークごとの上限（60件）に、荒らしではない利用で当たったら上げる。アカウントのチャレンジが200件に近づく人が出たら（9か月ほどかかる）、ページ分けで上限を外す。アラームの費用が問題になったら `DynamoThrottles` をテーブル単位の2つにする
