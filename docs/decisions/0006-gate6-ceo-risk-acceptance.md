# 0006. Gate 6 は実機の裏付けなしで通し、PILOT に進む（CEO のリスク受け入れ）

- Status: Accepted
- Date: 2026-10-07
- Decider: CEO（Mizuki。2026-10-07 に AI PM とのセッションで、A 再確認 / B このまま進む のうち「B」と回答）
- PROCESS.md との関係: §2 では Gate 6 の判定者は AI QA で、条件を満たすまで次に進まない。これはその例外で、根拠は §1 の本番公開の CEO の最終判断。他のサービスがこの例外を使うときも、同じように ADR に残す

## Context

Gate 6（[#4](https://github.com/mizuki-majima/try_something_new/issues/4)）は9項目中8項目が済み、残りは実機（iPhone Safari・Android Chrome）での Live smoke（[#8](https://github.com/mizuki-majima/try_something_new/issues/8)）だけだった。CEO は実機で確かめ、#4 に「いい感じに動いてるからパスしていいよ」とコメントした。

AI QA（別エージェント）が本番のログで裏付けを取ったところ、実機確認の時間帯に本番が受けたのはアカウントなしの閲覧6件（みんな・レシピ）だけで、チャレンジの開始・印・応援・進捗の公開 OFF・通知の許可とテスト・削除は0件だった。「同期済み」はサーバーにアカウントとチャレンジができて初めて出るので、CUF-1・CUF-1 E・CUF-3 は本番では行われていないと読める。CUF-2 は AI がテスト用のバックアップを渡していなかったのでできない状態だった。Web Push は本番で一度も購読・送信されていない。

AI 側の確認（通報 → 非表示 → 復元、アカウント削除、管理画面、ログに秘密情報・個人情報なし、5xx 0件、アラーム・通知・予算・DynamoDB の上限・SSM）はすべて問題なかった。自動テスト（CI の E2E 58件、Chromium）と本番の自動スモーク（Chromium、スマホ幅と PC 幅）は通っている。

AI QA の判定は「未達」（不具合は見つかっていないが、実機で書き込みが行われたかは本番のログからは分からない。条件がそろっていない）。調べたのは本番の API とリマインダーのログの 2026-10-07 06:30〜07:10 UTC（実機確認の時間帯）と、スタックの作成以降の全体。CEO に A（30分の再確認。AI がログを見ながら1項目ずつ確かめる）と B（このまま進み、リスクを受け入れる）を示し、AI は A を推奨した。B は、ADR 0005 で「やり直しに1か月かかる」として選ばなかった案（実機の確認を後回しにして招待する）にあたる。

## Decision

CEO が **B** を選んだ。Gate 6 は **CEO のリスク受け入れで通過**とし、Phase を PILOT にする。AI QA の PASS ではないことをここに残す。

受け入れたリスク:

- iPhone（WebKit）と Android の実機で、開始 → 押す → 同期（CUF-1）、オフラインからの同期（CUF-1 E）、振り返りとカード（CUF-2）、1日組と応援（CUF-3）が動く裏付けがない（自動テストは Chromium だけ）
- Web Push（テスト通知・定時のリマインド・iPhone のホーム画面アプリ）が本番で端から端まで動く裏付けがない
- ホーム画面アプリをオフラインで開けるか、実機でのコンソール・CSP のエラー、LINE と X でのリンクのプレビューも、実機では確かめていない

代わりに行う見張り（AI PM）。**AI は呼ばれたときしか動かない**ので、招待の日と 2026-11-01（日）は CEO が AI のセッションを開く:

- 招待を送った日と **2026-11-01（1日組の初日）** に、本番のログで参加者の操作（アカウント作成・チャレンジ作成・印・通知の購読）が届いているか、4xx / 5xx が増えていないかを確かめる。開始の操作が届いていない・失敗が多いときは、すぐ CEO に報告し、原因を調べる（[#8](https://github.com/mizuki-majima/try_something_new/issues/8) をこの見張りの Issue にする）
- 定時のリマインドが送られているか（リマインダーのログの送信数）を、最初の1週間（11/1〜11/7）はセッションのたびに確かめる（ai-product-org の services/try-something-new/README.md の「セッションのたびに確認すること」に入れた）
- **見張りの限界**: API のログは経路・状態・時間・ユーザーの ID の先頭だけで、端末（iPhone / Android）は分からない。CloudFront のアクセスログもない。iPhone だけの失敗は「操作が来ない」という形でしか見えない。そこで、CEO が 11/1 に参加者へ「上の表示が『同期済み』になっているか」を聞き、非公開の pilot-log に端末の種類と一緒に記録する

## Consequences

- 招待を送れる。最初の1日組は 2026-11-01 開始のまま
- iPhone だけの不具合があると、参加者の最初の数日で見つかることになる。PILOT は1日組1回なので、見つかるのが遅いと判定（Gate 7）に響く。初日の見張りと参加者への確認で早く気づくことで影響を小さくする
- docs/test-plan.md の「Live smoke は初回公開前」は、この PILOT では行わなかった（この ADR の例外）。一般公開（LIVE）の前には行う（#13 で手順を強化）
- Gate 7 の判定では、実機での CUF が参加者の利用で確かめられたかも見る（[#5](https://github.com/mizuki-majima/try_something_new/issues/5)）
- **見直す条件**: 初日の見張りで開始や同期の失敗が見つかったら、招待した人への連絡（CEO）と修正を最優先にし、必要なら1日組を12月にずらすことを CEO に諮る
